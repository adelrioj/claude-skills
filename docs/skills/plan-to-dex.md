# `/plan-to-dex`

Translates a Superpowers implementation plan into a [dex](https://github.com/francescoalemanno/dex)-compatible `plan.md`, imports it via `dex import`, and runs dex's `apply`/`review` loop end to end. Backend is fixed to codex; the skill never writes `.dex/config.json`. dex 0.4.9 has **no** `--model` flag and no effort option, so the only per-phase lever is which `clis` entry `--cli` names: `apply` runs `codex-gpt-5.6-luna-high`, `review` runs `codex-gpt-5.6-sol-high` — the cheap fast model implements, the frontier model reviews, both pinned, so neither phase inherits from `~/.codex/config.toml`. Step 4's preflight provisions both into `~/.config/dex/config.json` idempotently and additively, deriving each entry's `-m`/effort args from its own name, so the user needs no setup. Each phase resolves in one expansion, three-way — `$DEX_CLI_BUILD`/`$DEX_CLI_REVIEW` (an entry you named) beats `$CODEX_MODEL_*`+`$CODEX_EFFORT_*` (which become the `codex-<model>-<effort>` entry Step 4 provisions on demand) beats the phase default. Step 4 never provisions a `$DEX_CLI_*` name — auto-creating one would turn a typo into a silently-working backend. **Pinning a slug is a deliberate tradeoff** (ids age, entitlements vary), so Step 4 gates each pair against `~/.codex/models_cache.json` and refuses to write an entry the account cannot run; the gate is skipped, not failed, when that cache is absent — see `docs/codex-tuning.md`. One source Task = one `### Task N:` heading = one dex iteration. Output: `tasks/dex-plan.md`. Requires the `dex` and `codex` CLIs. Refuses to run `dex apply` on `main`/`master` — resolves a feature branch first.

**Prerequisite the skill states but does not satisfy: under `permissions.defaultMode: auto`, `dex apply` needs an explicit Bash allowlist entry.** Every backend provisioned here runs `codex exec --yolo --ephemeral` — an approval-gate-disabled agent loop that spawns further agents — and Claude Code's auto-mode security classifier refuses commands of that shape under **[Create Unsafe Agents]**. A live run had the provisioning write, `dex --cli codex apply`, and even a bare `cat ~/.codex/config.toml` issued next to a dex command all denied in one session. Step 4's check 3 probes for it with a no-op of the same shape (`dex --cli <entry> apply --help`) so the run stops in seconds instead of after a full translation pass, and `/ship-it` carries the same probe at preflight check 3 because its Step 4 runs this skill inside a subagent whose whole output is a three-field contract. **No allowlist entry is recommended anywhere in this repo, deliberately** — what the classifier refuses is a real thing to refuse on hosts where an autonomous pipeline holds push rights, so whether to open that gate is the operator's security decision and the settings live in their infra, not here. A classifier refusal is also **not** a confirmation gate: there is no prompt and no yes to give, so `/ship-it`'s "treat every confirmation gate as an answered yes" rule explicitly excludes it — a denial is reported as `failed` with its remediation, never rephrased, re-run, or inlined around.

## Conventions

- `/plan-to-dex` pins the dex backend to codex and never writes `.dex/config.json` — dex owns all execution state under `.dex/`. The config it does write is two additive, idempotent `clis["codex-<model>-<effort>"]` keys in the user's *global* dex config, so the two phases can run on different models — dex exposes no flag for it. Model *and* effort are pinned per phase (`gpt-5.6-luna` @ `high` builds, `gpt-5.6-sol` @ `high` reviews); since slugs age and entitlements vary, each pair is gated against `~/.codex/models_cache.json` before an entry is written
- BOTH `dex apply` and `dex review` are long-running (each exceeds the 10-min foreground Bash ceiling) — `/plan-to-dex` Step 6 mandates the same foreground poll-to-completion loop for each (re-run the phase, re-read `.dex/plan.md`, until all checkboxes `[x]` or terminal; `dex review`'s terminal includes the codex-quota case once apply is fully done and ≥1 reviewer pass has written findings) and forbids `run_in_background`/`Monitor`/"arm a watcher and yield". The guard has teeth via a **mandatory pre-return checklist** — the invocation must run and report `grep -c '\[ \]' .dex/plan.md` → `0`, a **worktree-scoped** live-worker check empty, and per-task dex commits present before returning. The live-worker check must stay scoped — `pgrep -f '[d]ex --cli codex|[c]odex exec'` piped through `lsof -a -d cwd -p <pid>` to keep only processes rooted in this worktree. A bare `pgrep -fl 'dex --cli codex|codex exec'` is wrong twice over: it matches concurrent `/ship-it` runs in *sibling* worktrees (turning a per-session completion gate into a machine-global one, so a finishing run either spins forever or reaps another run's dex), and it matches the command line of the shell running the check itself. Bracketing the first character kills the self-match; `lsof -d cwd` kills the cross-session match. The skills also state outright: never kill, signal, or wait on a process you did not start. `/ship-it`'s execute-and-report subagent prompt carries the identical FORBIDDEN list + pre-return checklist, because a subagent's backgrounded processes are reaped on return — backgrounding leaves only the dex setup commit
