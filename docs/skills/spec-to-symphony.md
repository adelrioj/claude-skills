# `/spec-to-symphony`

Hands a finished design spec to a [Symphony](https://github.com/openai/symphony) autonomous pipeline: puts the spec on the remote under the filename the pipeline will actually look for, then arms the **existing** ticket so the poller dispatches it. `issue.description` reaches a stage agent on every deployment and Linear **comments** reach none; **file attachments depend on the deployment** and must be read out of its config, never assumed (see the table below). Symphony contains no git code either way: cloning is the config's `after_create` hook, which runs **once** on first workspace creation, so anything not on the remote before first dispatch never arrives by that path. The skill's centre of gravity is Step 1 — **read the governing workflow config, never infer it.** Deployments disagree on every value the handoff depends on, and `active_states[0]` **is** the arming state, taken from the config rather than reasoned about. Every known config says *"seed the spec if it does not exist"*, so a filename mismatch does not error — the stage authors a competing spec and the brainstorming work is orphaned on the same branch while the pipeline runs to completion. Runs on the **Linear MCP** (the same server `/to-linear` uses); there is no workspace parameter, so the caller's token binds the one workspace this reads and writes.

**It no longer creates the ticket.** The premise it was written against — *"no ticket exists, no branch is pushed"* — stopped being true when `/linear-spec-ticket` became a station on the main line: by the time this skill runs, `/to-linear` has filed the ticket, `/linear-groom-ticket` has groomed it, `/linear-spec-ticket` has attached the spec, and `/spec-review-codex` has hardened the file on disk. A ticket created here therefore produced a **second ticket for work that already had one** — the grooming on one, the branch and spec on the other — every time the documented flow was followed. Steps 4 and 5 now resolve and verify an existing ticket instead, and creating is FORBIDDEN: since `save_issue` creates precisely when `id` is omitted, the rule is that every `save_issue` call here carries an `id`. No ticket at all means `/to-linear` first, not a ticket invented here.

**And it now owns the arming.** `/linear-spec-ticket` used to move the ticket to `Ready for Spec Review` — a real deployment's intake state — while pushing nothing and checking no project. That transition was removed from it; this skill's Step 9 does the arming, after Step 7's `git ls-tree` has proven the spec is on the remote branch and after the project has been set and read back. The original justification was *"it arms a pipeline that cannot see the spec"*, which is now deployment-specific; the decision stands on what is not — a leg that pushes nothing can prove nothing, and a ticket armed without a project is dispatched in no state at all. Step 5 also stops when the ticket is *already* in the arming state: that means a stage may have run without the spec, and re-arming is a no-op that reads as success.

**Every state name on this line is per-deployment and none is hardcoded** — the skill's Step 1 reads them out of the governing workflow config and STOPs if it cannot. Where an intake state is also filed into by something outside the deployment (an alerting job, a CI automation, another repo pinning it as an active state), that name is a cross-repo interface: grep for the literal before ever proposing a rename.

## What differs per deployment

Nothing in this list has a safe default and none of it is inferable from the repo, which is why Step 1 is a hard gate. **Never cache an answer between runs** — Symphony hot-swaps its `WORKFLOW.md` in place, so a re-render changes behaviour with no restart and no signal.

| Value | Why it differs | If you get it wrong |
|---|---|---|
| `active_states`, and which entry is the **intake (arming) state** | each deployment names its own Linear states; a rendered config may *also* name the intake state outright (e.g. an Ansible var like `symphony_intake_state`), and the explicit name wins | armed into a state the poller does not watch — Linear accepts the write, Symphony never dispatches |
| **spec path convention** | identifier-keyed (`<IDENT>-design.md`) vs date-slug (`<YYYY-MM-DD>-<slug>-design.md`) | the stage authors a competing spec; yours is orphaned on the branch |
| **branch** | usually Linear's own `branchName` lowercased, but some configs derive their own — it is stated, not assumed | the pipeline builds a branch your spec is not on |
| **attachments readable by the stage agent** | a property of the Symphony **build** (does `Tracker.Issue` carry an `attachments` field?), not of the config file | you count the attachment as delivery when nothing can read it |
| **spec-clobber guard on the first stage** | some stage bodies write the spec only *"if it does not exist"*, some write unconditionally | your pushed spec is overwritten by one authored from the description |
| poll interval | per deployment, seconds to tens of seconds | only affects how long you wait |

Two config **shapes** exist and both are readable, so inferring is never justified: a **file-based** config (one markdown file with YAML front matter) and an **Ansible-rendered** one (`WORKFLOW.md.j2` plus the role vars that fill it — read *both*; the intake state and a dry-run flag live in the vars, not the template). A config also commonly sits in the subdirectory of the service it governs (`elixir/WORKFLOW.md`), so the discovery search is not root-only.

**What the attachment answer changes about this skill's role, and what it does not.** Where attachments are readable the pipeline self-serves from `/linear-spec-ticket`'s attachment, so the branch push is redundancy rather than delivery — worth keeping (one commit; the spec becomes reviewable in the PR; the first stage finds the file present and skips authoring entirely), but no longer the thing that makes the handoff work. Where they are not, the push is still the only channel. **The arming is what nothing else on the line does**: set the ticket's project if it has none, move it into the intake state, prove both landed.

## Conventions

- **Step 1 is a hard gate, and it is the whole skill.** Baseline runs (no skill) both guessed and guessed *differently* — one read the wrong deployment's config and declared the brief wrong; the other could not read any config, admitted it was inferring, and hedged by satisfying two conventions at once. The skill therefore STOPs rather than proceeding on an inferred convention, and its Red Flags list names the three specific hedges verbatim ("probably…", "I'll satisfy both to be safe", "I'll push to `main` too")
- **The config discriminator is `hooks.after_create`, not the project slug.** Several deployments coexist on a dev machine and the front matter names a Linear project, which says nothing about which repo is built — so candidates are filtered by which repo they clone. Two candidates cloning the same repo is a STOP, not a tiebreak on recency or file location. Step 2 likewise **locates** the clone from that URL rather than assuming cwd is the target repo
- **Step 7 captures the bytes before branching; it never `git add -A`s and never branches from local `<default>`.** The spec can sit anywhere — **uncommitted in the worktree, which is what `/linear-spec-ticket` leaves behind** — or committed on local default, another branch, a detached commit; a branch cut from `origin/<default>` contains it in none of those cases, `git add -A` then stages nothing, the branch pushes without the spec, and the pipeline authors its own. `git fetch` (origin is routinely dozens of commits stale) → copy the file to a temp dir if it is in the worktree, else `git show <commit>:<spec>` → branch from `origin/<default>` → write it back at the Step 6 name → `git add` that **one path** (a switch carries every dirty file across, so staging a directory commits whatever else was lying around). An earlier revision hard-STOPped on an uncommitted spec, which made the documented `/linear-spec-ticket` → here handoff abort every time. **`git ls-tree -r --name-only origin/<branch>` must then show the spec before arming**, and the local-default reset happens only after that check — resetting first orphans the user's only copy to the reflog. A GREEN run caught this as a data-loss bug in the skill's first draft
- **Six values are extracted and printed from the config before anything else runs:** `tracker.provider.project_slug` (project match), `active_states` with its intake entry (arming state), the `hooks.after_create` clone URL (repo identity), the spec-path convention from the body prose, whether the stage prompt renders `issue.attachments` (and an attachment-fetch tool is allowed), and whether the first stage guards an existing spec. The clone URL check is the only cheap way to catch a spec committed in the wrong clone — normalize `git@github.com:owner/repo.git` and `https://…/owner/repo.git` to `owner/repo` and compare against `git remote get-url origin`. No safe default exists for the spec-path convention, so a config that omits it is a STOP; an unreadable attachment answer defaults to *not readable*, which costs nothing because the push happens either way
- **The arming state is resolved at runtime, never hardcoded** — `Todo` on one team vs `To Do` on another, which Linear treats as different states — by exact name equality with `active_states[0]`. The tracker's GraphQL filter is an exact `state: {name: {in: [...]}}` match, so a near-miss name yields a ticket that looks armed and is never dispatched. Symphony treats `active_states` as a **filter set and ignores its order**, so intake-first ordering is a convention for readers; where the config is Ansible-rendered the intake state is also named outright (`symphony_intake_state`) and the two must agree. No backlog state is resolved any more: nothing here creates a ticket, so there is nothing to park
- **The Linear MCP has no workspace parameter.** The caller's token binds the session to exactly one workspace, which the skill can neither select nor assert. `list_projects` returns only that workspace's projects, so a project that is not in the list means the connector is bound to the wrong workspace — a STOP, not a silent wrong-workspace write. Confirm the resolved project, and the identifier the `get_issue` read returns, against what you asked for
- **The ticket is resolved, verified, then armed last.** Step 4 takes the identifier from the invocation, the worktree, or the spec's `<IDENT>-` prefix and reads the issue once; Step 5 checks four things off that one response — the identifier is what was asked for, the **project matches the config's deployment** (a mismatch means the spec would land where no poller watches, or where the wrong one does; **no project at all** is recorded for Step 9 to set, never repaired in place), `branchName` is present, and the current state is not already the arming state. It also notes whether `<IDENT>-design.md` is attached: absent is not a blocker, but a human reading the ticket sees no spec and, on an attachment-reading deployment, the pipeline loses its second copy. A *stale* attachment matters more there than it used to — where the stage treats the attachment as outranking the description, `/linear-spec-ticket <IDENT> refresh` is what keeps it honest
- **Arming is two writes, project first, each read back.** Symphony's tracker filters `project` **before** `state`, so a ticket with no project matches the poller's query in *no* state: arming it dispatches nothing and logs nothing, and the orchestrator is indistinguishable from idle. MDZ-249 shipped out of the spec leg that way and needed manual repair before its first run. Step 9 therefore sets the project (only when Step 5 found none), reads it back, and only then moves the state and reads *that* back — a returned-without-error `save_issue` is not proof a field moved. The two never share a call: the project write is a repair, the state write arms an autonomous pipeline, and keeping them apart means a failed project write leaves the ticket parked and safe to retry
- **FORBIDDEN, from observed baseline behaviour and from the seam that produced this revision:** creating a ticket; arming before Step 7's proof; rewriting the ticket description; pushing to the default branch (one baseline proposed `git push origin main` as a hedge against not knowing the checkout strategy); landing the spec under a name the caller has not agreed to; delivering the spec path via a Linear **comment** (no stage reads comments; an attachment is a real channel on some deployments, but it is `/linear-spec-ticket`'s to write, not this skill's); inlining the spec into the description; assuming a workspace the token is not bound to
- **Entering at a later stage to dodge a spec-authoring first stage is forbidden** — that is inference wearing a workaround. The supported fix is a guard in the workflow config itself: *if the branch already carries a design spec, do not write a new one; validate it against the ticket description and advance.* Many configs already carry one, typically as an *"if it does not exist"* conditional on the first stage's spec write — but the skill re-reads and re-reports it every run rather than trusting that, because a guard that *was* present is exactly what a later edit removes unnoticed
- **A guard you have to write must be branch-scoped, and this is the subtle part.** `ls docs/superpowers/specs/*-design.md` and "newest by date prefix" both glob every spec in the repo including unrelated merged work — the moment one of them sorts later than yours, the stage hardens the wrong file and nothing errors. An **exact identifier-keyed path** is the strongest selector; where the convention is date-slug, use `git diff --name-only $(git merge-base origin/<default> HEAD)...HEAD -- 'docs/superpowers/specs/*-design.md'`, blocking on more than one hit. Step 7 (branch cut from `origin/<default>`, spec commit landed on it) is what puts the spec in that diff
- **The filename is the deterministic fix, description text is not.** When the config keys specs by identifier, landing the file *as* the path the stage computes beats instructing the stage out of a hardcoded path via the description. The rename lives in Step 7's destination path, so the caller's local file is never touched and an untracked spec needs no special handling — and in the ordinary flow there is nothing to rename, since `/linear-spec-ticket`'s `<IDENT>-design.md` already satisfies both known conventions. A declined rename is reported explicitly, because the run will otherwise look successful while a competing spec is authored
- **Step 8 appends to the description; it never authors one.** The old Step 8 rewrote the body because the same skill had just created it. That body is now a groomed, templated artifact — `/to-linear` filed it against the shared template and `/linear-groom-ticket` redrafted it against the same one — so the step adds a single `Design spec: <path>` line if it is missing and otherwise writes nothing. It appends with `save_issue`'s `patch` parameter rather than the `description` field — `description` replaces the whole body, and re-sending a groomed template verbatim to append one line is how a section gets silently dropped
- **Case matters on prefix-matched branches** — Linear's `branchName` is lowercased (`alejandrodelrio/tra-42-…`) while an `<IDENTIFIER>-*` remote match is uppercase. Use the config's branch form, not Linear's, whenever the config derives its own
- **Anything that makes the run a silent no-op is named in the final report** — a declined rename, or a deployment running with a dry-run flag set (an Ansible-rendered one typically carries it in its role vars, e.g. `symphony_dry_run`), which turns every stage into a comment-only run that lands nothing on the remote
