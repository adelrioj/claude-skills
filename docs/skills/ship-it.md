# `/ship-it`

Pure conductor that chains the existing units into one autonomous spec→PR pipeline. Seven-step sequential process: hardens the spec via `/spec-review-codex`, writes the implementation plan, executes it via `/plan-to-dex`, opens a PR with `/commit-commands:commit-push-pr`, then a `general-purpose` subagent runs the whole `/review-pr` panel and applies the CRITICAL/IMPORTANT fixes to the working tree — the built-in `/code-review` is `disable-model-invocation` and can't be called autonomously, so `/review-pr` (no such flag) is run inside the subagent instead (up to 3 review passes, conductor commits/pushes between them), then closes with a report-only `/architect-review-pr` completeness pass whose findings land in the final report; merging stays manual. A preflight (codex + dex on PATH, `pr-review-toolkit` + `commit-commands` + `superpowers` plugins present **via the `installed_plugins.json` registry**, spec located) is the sole hard abort; a non-fatal advisory check (`gh repo view --json viewerPermission`) warns up front when the active `gh` account cannot open the PR. The heavy steps (1/2/4/6) run as **subagents** that deliver a structured three-field contract by **writing it to a conductor-supplied path in `$RUN_DIR`** (a `mktemp -d` minted at preflight), keeping raw codex/dex/review output out of the conductor's context; Steps 3/5/7 run in the main loop, and Step 6's commit/push fix loop is driven by the conductor around its per-pass review-and-fix subagent. Never halts on quality findings; records any leftover issues in a final report. Requires the `codex` and `dex` CLIs plus the `pr-review-toolkit` and `commit-commands` plugins.

## Conventions

- `/ship-it` is a pure conductor — it invokes spec-review-codex, writing-plans, plan-to-dex, /commit-commands:commit-push-pr, and architect-review-pr LIVE and duplicates none of their logic; Step 6's subagent runs the `/review-pr` panel LIVE (not the built-in `/code-review`, which can't be model-invoked)
- `/ship-it`'s Step 6 gives the review-and-fix subagent the PR number as the review target — after the push, the branch's default review range (`@{upstream}...HEAD`) is empty — and the subagent runs `/review-pr` then applies the CRITICAL/IMPORTANT fixes to the working tree without committing; the conductor commits, pushes, and re-dispatches. `/review-pr` launches analyzers via the `Task` tool, so if the harness forbids a subagent spawning subagents the Step 6 subagent runs the review aspects inline instead
- `/ship-it` is best-effort and never halts on quality; the only hard abort is a failed preflight; a hard failure that makes the next step impossible skips downstream steps and jumps to the final report — it never fabricates a downstream artifact (no empty PR)
- `/ship-it` keeps no state in the workspace; everything it persists lives in `$RUN_DIR` (`mktemp -d`, minted and printed at preflight — **inside the session scratchpad when the harness provides one**, since scratchpad writes are pre-approved while a bare `/tmp` path can trigger a permission prompt, and a prompt inside an unattended subagent is a stall that produces no contract at all): each step's contract, Step 7's architect report, and the /handoff-style final report. `$RUN_DIR/artifacts/` also receives the dex by-products (`tasks/dex-plan.md`, `.dex/`) that Step 5 quarantines out of the PR — only when they are untracked *and* unignored, since a repo that tracks or ignores them has already decided
- **Two predicates that look right and are not.** (a) Step 4's zero-diff guard cannot be "clean tree and `HEAD` unmoved": the tree is already dirty pre-dispatch (Step 1's spec rewrite, Step 2's plan file) and `dex import --force` always commits, so that guard never fires and a scaffolding-only run sails into an empty PR — it must exclude `tasks/dex-plan.md`, `.dex/`, `docs/superpowers/` from both the `git log` and the `git status`. (b) Step 6's "fixes applied" test cannot be a merely non-empty tree: one leftover untracked file satisfies it on every pass and drives the loop to its 3-pass cap reporting fixes that never happened — hence the pre-dispatch snapshot diff
- **Step 6 must prove its review scope, not just its verdict.** `/review-pr`'s own command file scopes from the working tree (`git diff --name-only`), which is empty after Step 5 pushes — so its *default* behaviour on this branch is to review nothing and report clean, ending the loop as a false success. The conductor computes `git diff --name-only <base>...HEAD` itself, hands the subagent that explicit file list, and requires `reviewed: <N> of <SCOPE_N> files` back in `state`; a zero or missing count is a `failed` pass, never a clean one
- `/ship-it` runs the heavy steps (1/2/4/6) as subagents that deliver a three-field contract (outcome/state/notes) **as a file** at a path the conductor fixes up front and passes in, keeping raw codex/dex/review output out of the conductor's context; Steps 3/5/7 run in the main loop, and Step 6's commit/push fix loop wraps its per-pass review-and-fix subagent
- **A subagent's final message is a single-delivery, unrecoverable channel** — observed runs had 5/5 and 4/5 subagents complete their work and end with a bare `idle_notification` and no contract, and a `SendMessage` re-ask recovered none. So the contract file is the carrier and the return message is corroboration; subagents are told to write the file **incrementally** (outcome/state early, notes appended as findings land) so it survives an agent that idles mid-work, not just one that idles at the end
- **The chained units were written for interactive use and will try to ask the subagent questions — the dispatch prompt pre-answers all of them.** `plan-to-dex`'s `Proceed? [y/N]`, its plan-validation and quality-gate asks; `spec-review-codex`'s "retry or skip?" on a 120s codex timeout (answer: retry once, then `failed`); and above all `writing-plans`' closing **"Which approach?" Execution Handoff**, whose answers attach a REQUIRED SUB-SKILL (`subagent-driven-development` / `executing-plans`) — a Step 2 subagent that self-answers it starts *implementing the plan*, duplicating Step 4's dex run on the same branch. The prompt therefore says: no user is reachable, every gate is a pre-approved yes, and Step 2 STOPS the moment the plan file is written
- Every step also has a **ground-truth predicate** the conductor checks in its own shell — a findings file newer than dispatch (1), `test -f <plan>` (2), commits-after-`HEAD_0`-or-tree-changes **excluding the pipeline's own by-products** (4), the working tree **differing from a pre-dispatch snapshot** ⇒ fixes applied (6), `test -f` the architect report (7). Two rules keep these honest: **anchor every predicate to a value captured before dispatch** (an mtime, a commit SHA) — an unanchored `ls`/`git log` check is satisfied by a previous run's artifact, which is the stale-artifact bug wearing a different hat — and **prove the step RAN, not that it CHANGED something**, since a spec review that passes on iteration 1 rewrites nothing and that best-case outcome must not read as failure. Git is the authority, the contract is the narrative: a missing contract with work on disk is `finished-with-notes (contract lost — state reconstructed from git)` and the run continues; only "no contract AND no work" changes control flow. The conductor **never** re-asks, polls `TaskOutput`, or re-dispatches — the work completed, only reporting failed
- **No artifact is ever located by glob.** Contract, architect report and final report paths are all fixed at preflight, because a timestamped pattern like `architect-review-pr-*.md` is satisfied by a stale report from a previous session on a different ticket — silently adopting one is worse than having none. The final report names any step whose contract was lost or disagreed with its predicate, so a lossy run can't read as a clean one
- **Codex tiers are pinned by the chained units, validated at preflight, and printed once.** Nothing here needs setup — spec-review and dex `review` run at `xhigh`, dex `apply` inherits the machine's config (`docs/codex-tuning.md`). Step 0 validates `CODEX_EFFORT_REVIEW` / `CODEX_EFFORT_BUILD` / `DEX_CLI_BUILD` / `DEX_CLI_REVIEW` **only if the user set them**, because both backends fail open: `codex exec -c model_reasoning_effort=garbage` runs happily and `dex --cli nope` prints `unknown CLI` and **still exits 0**, so a typo silently runs the whole pipeline at the wrong tier. Step 0 also `echo`s the resolved tiers and the Final Report repeats that line — `plan-to-dex` prints its own `Backend:` line but runs as a Step 4 subagent whose output is compressed to a three-field contract, so without the conductor's own echo the tier is invisible for the entire run. Never resolve the `${…:-…}` fragments to a concrete tier; type them literally
- `/ship-it`'s Step 7 (architect-review-pr) is record-only — the conductor never fixes architect findings, it puts them in the final report; and since architect-review-pr reviews the branch diff (not the PR object), a failed PR creation skips only Step 6, while a zero diff from Step 4 skips Steps 5-7
